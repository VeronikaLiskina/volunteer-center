# Изменения рабочих сценариев

Стек и цепочка routes → services → repositories → models сохранены.

## Реализованные правила

- Все четыре формы телефона используют `PhoneInput`: маска при вводе и вставке, редактирование в середине строки, нормализованный номер в запросе. Серверная нормализация сохранена.
- Выполнение хранит `is_completed` и `failure_reason`. Успех переводит назначение в `completed`; неуспех — в существующий `cancelled`. Причина обязательна для неуспеха и запрещена для успеха. Исход можно записать только один раз; PATCH уточняет текст, но не меняет исход. Старые клиенты без `is_completed` сохраняют прежнее поведение.
- `available_from` / `available_to` задают ежедневное окно в местном времени центра. Пустая граница не ограничивает соответствующий край суток. Проверяется весь интервал услуги; пересечения запрещены, соседние интервалы разрешены. Текст `note` только показывается. Изменение доступности, нарушающее текущие назначения, отклоняется.
- Деактивация требует замены для всех незавершённых назначений, включая просроченные. Предпросмотр возвращает подходящих кандидатов без ограничения пагинацией. При подтверждении сервер заново проверяет состав назначений и доступность. Переназначения, уведомления и смена статуса фиксируются одной транзакцией; ошибка откатывает всё.
- Архивация устанавливает `suspended_by_archive` только у назначений `assigned` / `overdue`. Даты, волонтёры и исходные статусы остаются в тех же строках. Приостановленные назначения исключены из текущих списков, сводок, напоминаний и отчётов; выполнить их нельзя. История и ранее отменённые услуги сохраняются.
- Восстановление снимает только признак архивации. Если прежний исполнитель занят, неактивен или недоступен, вся операция отклоняется до разрешения конфликта. Независимая отмена приостановленной услуги очищает признак архивации, поэтому её восстановление не возвращает. Повторные вызовы безопасны.
- Просроченность определяется после наступления планового **начала**, как в прежних отчётах и уведомлениях. `CareProcedure.status` — единое вычисляемое свойство SQLAlchemy для сериализации и SQL-фильтров/агрегатов. Сохранённый столбец `status` не требует фоновых обновлений: ещё назначенная услуга в прошлом возвращается как `overdue`. Закрытые и приостановленные услуги не переходят в просроченные.
- `DateInput`, `formatDate`, `formatDateTime` обеспечивают `ДД.ММ.ГГГГ` в формах, списках, карточках, уведомлениях и отчётах. В API остаётся ISO. Excel сохраняет русский формат дат.
- Отчёт об уходе содержит животных и распределение услуг; отчёт о волонтёрах — участие и нагрузку; отчёт об исполнении — статусы, включая отдельное невыполнение. Все данные отобраны по плановой дате и типу услуги. Минуты обозначены как **плановые минуты выполненных услуг**, поскольку фактическая длительность не хранится. XLSX и PNG соответствуют выбранному типу, сохранённые снимки отчётов поддерживаются.

## Миграция и API

`backend/migrations/versions/0012_workflow_rules.py` добавляет пять полей и ограничения исхода/доступности. Старые выполнения становятся успешными; незавершённые назначения уже архивных животных помечаются приостановленными. Данные не удаляются. Есть downgrade.

Новые endpoint-ы:

- `GET /api/v1/volunteers/{id}/deactivation-assignments` — назначения и кандидаты.
- `POST /api/v1/volunteers/{id}/deactivate` принимает `{"reassignments": [{"procedure_id": 1, "volunteer_id": 2}]}`; без назначений допустимо пустое тело.
- `POST /api/v1/animals/{id}/restore` — восстановление.

Операции изменения расписания используют общий PostgreSQL advisory transaction lock. Для масштаба учебного центра это простой способ исключить гонки между назначением, изменением доступности, архивацией и деактивацией. Транзакции разных изменений расписания выполняются последовательно.

## Основные изменённые файлы

Backend: модели, схемы и сервисы `care_procedure`, `procedure_execution`, `volunteer`, `animal`; репозитории назначений, выполнения, аналитики и уведомлений; маршруты животных и волонтёров; сервис аналитики.

Frontend: общие `PhoneInput`, `DateInput`, `VolunteerDetails`, `DeactivateVolunteerDialog`; формы животных, волонтёров, назначения и выполнения; списки животных/волонтёров; страницы входа/регистрации; компоненты аналитики, результатов и уведомлений; API и типы.

Проверки: `backend/tests/test_workflow_rules.py`, `frontend/tests/workflow-rules.spec.ts`; обновлены существующие тесты аналитики, назначений, волонтёров, входа и регистрации. Проверяются API-валидация, интервалы, атомарность и rollback, повторные операции, история, миграция старых данных, отчёты и экспорт, ввод и отображение в браузере.

## Запуск

Из `backend`: `python -m alembic upgrade head`, `python -m alembic check`, `python -m pytest -q`.
Из `frontend`: `npm run build`, `npm run lint`, `npm run test:e2e`.

При проверке использован отдельный локальный PostgreSQL 17 с ICU locale `ru-RU`; каждый pytest-тест дополнительно изолирован транзакционной схемой. База из `backend/.env` на `localhost:55433` была недоступна. `.env` не изменялся; перед запуском приложения нужно применить миграцию к его базе.
