# АСУВЦ «Лапка»

Учебное веб-приложение для управления волонтёрским центром помощи животным. Реализованы вход и роли, главная панель, health-check, учёт животных и волонтёров, планирование и выполнение процедур ухода, уведомления, аналитика и XLSX-отчёты. Стек: FastAPI, PostgreSQL, SQLAlchemy AsyncSession, Alembic, React, TypeScript, Vite, SCSS/БЭМ.

## Требования

- Python 3.11+
- Node.js 20.19+ или 22.12+
- Docker с Docker Compose

## 1. PostgreSQL

При первом запуске скопируйте корневой `.env.example` в `.env`, задайте пароль и те же реквизиты в `backend/.env`. Уже настроенные `.env` не перезаписывайте. Затем запустите базу:

```bash
docker compose up -d postgres
```

По умолчанию PostgreSQL публикуется на порту `55432`, чтобы не конфликтовать с уже установленным локальным PostgreSQL. Порт можно изменить через `POSTGRES_PORT` одновременно в корневом и backend-файлах `.env`.

## 2. Backend и миграции

Команды выполняются из каталога `backend`:

```bash
python -m venv .venv
# Windows PowerShell
.venv\Scripts\Activate.ps1
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
```

Если `backend/.env` отсутствует, скопируйте `backend/.env.example` и согласуйте пароль с корневым `.env`. Примените миграции, заполните справочники и запустите API:

```bash
alembic upgrade head
python -m app.seed
uvicorn app.main:app --reload
```

Миграция `0001_animal_registry` создаёт таблицы животных и справочников, `0002_volunteers` — таблицу волонтёров, `0003_volunteer_duplicate_key` добавляет защиту контактов от конкурентных дублей, `0004_care_procedures` — типы и плановые процедуры ухода, а `0005_procedure_executions` — фактические результаты выполнения. Seed можно запускать повторно: он добавляет отсутствующие типы животных, породы и типы процедур через `ON CONFLICT DO NOTHING`, не создаёт рабочие записи и не перезаписывает справочники.

Если PowerShell блокирует активацию окружения, запускайте команды напрямую: `.venv\Scripts\python.exe -m pip install -r requirements.txt`, `.venv\Scripts\python.exe -m alembic upgrade head`, `.venv\Scripts\python.exe -m app.seed`, `.venv\Scripts\python.exe -m uvicorn app.main:app --reload`.

## 3. Frontend

Перед первым входом примените миграции командой `alembic upgrade head` и создайте координатора из каталога `backend`. Вход выполняется по уникальному номеру телефона, ФИО вводится отдельно и сохраняет регистр:

```bash
python -m app.create_user "+79991234567" --full-name "Иванова Анна Петровна" --role COORDINATOR
```

Команда дважды запрашивает пароль скрытым вводом (от 12 символов); пароль не передаётся аргументом командной строки и не записывается в исходники. Стандартных паролей нет. CLI остаётся способом создать первого координатора или выдать учётную запись вручную. После создания карточки волонтёра координатором можно выдать ему учётную запись:

```bash
python -m app.create_user "+79991234568" --full-name "Петров Иван Сергеевич" --role VOLUNTEER --volunteer-id 1
```

Укажите ID существующей карточки. Один волонтёр связан с одной учётной записью. Роли: `COORDINATOR` — реестры, назначения, справочники, аналитика и уведомления; `VOLUNTEER` — только свои назначения, их выполнение и свои уведомления. Сервер проверяет роль и принадлежность объекта, в том числе при прямом обращении к API.

Самостоятельная регистрация доступна по ссылке «Зарегистрироваться» на странице входа (`/register`). Пользователь вводит ФИО, телефон, пароль от 12 символов и повтор пароля. Роль не выбирается: создаётся неактивная учётная запись со статусом `pending` и без роли. Координатор открывает раздел «Заявки» (`/registrations`), выбирает роль «Волонтёр» или «Координатор» и подтверждает заявку либо отклоняет её. В разделе есть фильтр по статусу и постраничный список. Сохраняются дата рассмотрения и ID координатора. До подтверждения сессия не выдаётся, рабочие API недоступны; при правильном пароле вход сообщает об ожидании или отклонении.

При подтверждении волонтёра используется активная карточка с совпадающими нормализованными ФИО и телефоном либо создаётся новая. Неактивную карточку сначала нужно активировать; карточка, связанная с другой учётной записью, не переиспользуется. Пароль и регистр ФИО учётной записи при подтверждении сохраняются. Повторное рассмотрение заявки возвращает конфликт, отклонённые заявки остаются в истории; номер остаётся закреплён за учётной записью. Миграция `0009_registration` отмечает ранее созданные аккаунты как подтверждённые и сохраняет их доступ. API: `POST /api/v1/auth/register`, `GET /api/v1/registrations?status=pending`, `POST /api/v1/registrations/{id}/approve` с `{"role":"VOLUNTEER"}` или `{"role":"COORDINATOR"}`, `POST /api/v1/registrations/{id}/reject`. Все операции рассмотрения доступны только координатору.

Самостоятельное восстановление доступно по кнопке «Забыли пароль» на странице входа (`/forgot-password`). Пользователь указывает телефон, получает шестизначный SMS-код и вводит новый пароль дважды. Код действует 5 минут, допускает 5 попыток и используется один раз. Повторная отправка разрешена через 60 секунд и отменяет предыдущий код. После смены пароля старые сессии завершаются; роль, назначения и статус рассмотрения заявки сохраняются. Восстановление не подтверждает регистрацию автоматически.

Перед использованием установите зависимости (`python -m pip install -r requirements.txt`) и примените миграцию `0010_password_reset` командой `python -m alembic upgrade head` из каталога `backend`. Отправка подключена к [SMS.ru](https://sms.ru/docs/api/api_group_sms/send). В локальном `backend/.env` задайте:

```dotenv
SMS_RU_API_ID=ваш_ключ_из_личного_кабинета_SMS_RU
SMS_RU_SENDER=
PASSWORD_RESET_SECRET=отдельный_случайный_секрет_не_короче_32_символов
```

Для генерации `PASSWORD_RESET_SECRET` выполните `python -c "import secrets; print(secrets.token_urlsafe(48))"` и сохраните результат только в `.env`. `SMS_RU_SENDER` можно оставить пустым для отправителя по умолчанию либо указать согласованного с провайдером отправителя. Перезапустите backend. Для реальной доставки нужны рабочий аккаунт провайдера, доступная отправка и достаточный баланс. Без ключа и секрета API возвращает ошибку доступности; приложение не показывает и не записывает SMS-коды в логи. В тестах отправка подменяется, реальные SMS не отправляются.

API восстановления: `POST /api/v1/auth/password-reset/request` с `{"phone":"+79991234567"}` возвращает `request_id`, нейтральное сообщение, `resend_after` и `expires_in`; `POST /api/v1/auth/password-reset/confirm` с `{"request_id":"…","code":"123456","password":"новый пароль"}` возвращает `204` при успехе. Неизвестный номер получает такой же успешный ответ запроса кода, без отправки SMS. В БД хранится HMAC кода с отдельным серверным секретом; код привязан к запросу, телефону и текущему паролю. Смена телефона или пароля делает ранее выданный код непригодным.

Ограничения запросов хранятся в PostgreSQL и действуют для всех процессов: 1 запрос в минуту и 5 в час на телефон, 20 в час на IP, 200 в сутки суммарно; проверка кода — 30 запросов в минуту на IP. Неуспешные запросы тоже учитываются. При превышении возвращаются `429` и `Retry-After`. Для размещения за reverse proxy разрешайте обработку forwarded-заголовков только от доверенного прокси, чтобы лимит использовал реальный IP. Записи восстановления и счётчики удаляются при новых запросах спустя сутки после истечения срока.

Резервный административный способ из каталога `backend`: `python -m app.create_user "+79991234567" --reset-password`. Команда дважды запрашивает новый пароль, сохраняет ID, роль и назначения пользователя и отзывает его старые сессии. Флаги роли, ФИО и волонтёра при смене пароля не передаются.

Телефоны нормализуются в `+7XXXXXXXXXX`: принимаются варианты с `8`, `+7`, пробелами, скобками и дефисами. Один номер принадлежит только одной учётной записи; одинаковые ФИО разрешены. В шапке отображается `full_name`, телефон не используется как имя. Тело запроса входа: `{"phone":"+79991234567","password":"…"}`; ответ пользователя содержит `phone` и `full_name` вместо прежнего `login`.

Миграция `0008_user_phone_name` сохраняет ID, пароль, роли и связи старых записей. Для связанных волонтёров берутся ФИО и уникальный телефон из карточки. Если телефон неизвестен или совпадает у нескольких учётных записей, его необходимо задать явно; вымышленные номера не создаются. Для настройки существующей записи: `python -m app.create_user "+79991234567" --update-user 1 --full-name "Иванова Анна Петровна"`. Команда сохраняет пароль и роль; смена телефона завершает старые сессии. ФИО и телефон учётной записи управляются отдельно от контактных данных карточки волонтёра.

Пароли хешируются scrypt (`N=131072, r=8, p=1`, случайная соль). Вход выдаёт случайный bearer-токен на 8 часов; в БД хранится только SHA-256 токена. Выход отзывает сессию, `is_active=false` немедленно запрещает использование всех сессий пользователя. Frontend хранит токен в `sessionStorage`, передаёт его в `Authorization` для JSON и XLSX и возвращает на страницу входа при `401`. API: `POST /api/v1/auth/login`, `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`.

Команды выполняются из каталога `frontend`:

```bash
npm install
npm run dev
```

URL backend берётся из `VITE_API_URL`; пример — в `frontend/.env.example`. Если нужен свой адрес, создайте `frontend/.env`. Для Windows при блокировке `npm.ps1` используйте `npm.cmd`. PostgreSQL работает в Docker, backend и frontend запускаются локально.

## Аналитика и отчёты

Единая страница `/analytics`: параметры → период → услуга из серверного справочника → «Сформировать отчёт» → сводка и диаграммы → «Выгрузить отчёт» (XLSX) или «Скачать PNG». PNG включает название, применённый период и услугу, показатели, диаграммы и рейтинг волонтёров. Картинка формируется в браузере из показанного результата, с шириной 2400 пикселей и полной высотой; меню и форма фильтров в неё не входят. Старый адрес `/reports` перенаправляет на неё. Существующие компоненты фильтров, результатов, диаграмм и XLSX-генератор переиспользованы.

`GET /api/v1/reports` и `GET /api/v1/reports/export.xlsx` принимают `report_type`, `date_from`, `date_to`, необязательный `procedure_type_id`. Отсутствующий тип означает «Все услуги», неизвестный ID и обратный диапазон дают `422`. `/analytics` без параметров сохраняет общий обзор для главной; при передаче периода возвращает ту же отфильтрованную сводку, что `/reports`.

Все показатели отчёта используют плановую дату назначения, включая обе границы. График выполнений группирует факты выполнения выбранных назначений по **плановому месяцу**, даже если фактическое выполнение было раньше/позже; итог совпадает со счётчиком выполненных. Животные и волонтёры — уникальные участники назначений всех выбранных статусов. Активность волонтёров показывает количество фактов выполнения, включая нулевую активность участников. Просроченными считаются явный статус `overdue` и ещё назначенные процедуры с прошедшими плановыми датой/временем. Это текущая оценка, не исторический снимок статусов на конец периода.

XLSX содержит период, название услуги, семь показателей, распределение услуг, помесячные данные и активность волонтёров. Добавлены закрепление строк и настройки печати A4 по ширине страницы. Ответ отчёта содержит `report_id`: сервер сохраняет результат на 24 часа в `report_snapshots` (миграция `0007_report_snapshots`). Frontend передаёт этот ID и применённые фильтры при выгрузке. Файл точно соответствует показанному результату, даже если параметры формы или назначения уже изменились. Доступ к сохранённому отчёту есть только у создавшего его пользователя; после истечения срока требуется сформировать его заново. Просроченные результаты удаляются при следующем формировании. Старый API экспорта без `report_id` продолжает строить файл по текущим данным.

## Уведомления

Существующая кнопка в шапке открывает список реальных событий. `notifications` хранит получателя, процедуру, вид события, время и состояние прочтения. Создание/изменение/отмена сохраняют уведомления в одной транзакции с назначением. При переназначении прежний исполнитель получает сообщение о передаче, новый — о назначении; координаторы получают события центра.

`GET /api/v1/notifications?limit=20&offset=0` возвращает только уведомления текущего пользователя и общее число непрочитанных; `PATCH /api/v1/notifications/{id}/read` отмечает своё уведомление прочитанным. При чтении списка сервер проверяет незавершённые назначения: ближайшие 24 часа и просрочку. В открытом приложении проверка повторяется каждые 30 секунд. Уникальный ключ `(user_id, procedure_id:revision:kind)` защищает от повторов при опросе и конкурентных запросах. Фоновая рассылка, email и push не используются; без открытого приложения новые напоминания появятся при следующем входе. Плановые даты/время интерпретируются в локальном часовом поясе сервера центра (для текущего окружения — Asia/Irkutsk).

## Учёт животных

Список, форма и справочники разделены по маршрутам: `/animals`, `/animals/new`, `/animals/{id}/edit` и `/animals/dictionaries`. На дочерних страницах есть закрытие с возвратом к списку. В списке доступны поиск по подстроке клички, тип, статус и страницы по 20 записей.

Архивирование требует подтверждения, сохраняет запись и делает её доступной только для просмотра. Повторное архивирование безопасно. Статус новой карточки задаёт сервер: `in_care` («Под опекой»); архивной — `archived` («В архиве»). Реестр доступен только координатору после входа.

Поля `id`, `status`, `duplicate_key` запрещены в запросах создания/редактирования. `PATCH` принимает только изменяемые поля, пропущенные значения сохраняются; необязательные поля можно очистить через `null`. Обязательные поля не принимают `null`.

Телефон необязателен; принимаются российские номера из 11 цифр с начальной 7/8, допускаются пробелы, скобки и дефисы. Хранение — в виде `+79991234567`. Вес — `Numeric(6, 2)` / Python Decimal, в JSON передаётся строкой: `"4.25"`. Допускается 0 < вес ≤ 9999,99 кг, до двух десятичных знаков. Год рождения — от 1900 до текущего года.

Правило очевидного дубликата: совпадают кличка, тип, порода, год рождения, ФИО и телефон ответственного лица. Регистр и лишние пробелы в кличке/ФИО игнорируются, телефон нормализуется. Вес, примечание и статус не влияют на совпадение. Полное совпадение с архивной карточкой также блокируется. Животные с одинаковой кличкой, но разными данными владельцев допускаются. Без данных владельца это эвристика: для животных-тёзок одного типа/породы и года потребуется уточнить ответственное лицо; это не надёжная идентификация по чипу.

Сервер формирует SHA-256 ключ из этих нормализованных данных и хранит его в уникальном столбце `duplicate_key`. Предварительная проверка даёт понятный конфликт, уникальность в PostgreSQL дополнительно защищает от одновременных запросов. Ошибки ссылок/полей возвращаются как `422`, дубли и изменение архивной карточки — `409`, отсутствующая карточка — `404`.

## Учёт волонтёров

Карточка содержит только ФИО, обязательный российский телефон, необязательное примечание и серверный статус. Создание и редактирование открываются на отдельных страницах `/volunteers/new` и `/volunteers/{id}/edit`, закрытие возвращает к списку. В списке доступны поиск по ФИО, фильтр статуса и пагинация.

Новый волонтёр всегда создаётся со статусом `active` («Активен»). Статус нельзя передать в `POST` или обычный `PATCH`: он изменяется только действиями активации и деактивации. Деактивация требует подтверждения, не удаляет запись и идемпотентна; неактивные волонтёры не возвращаются endpoint-ом `/volunteers/active`. Физического удаления нет.

Телефон принимается в форматах `+7 (999) 123-45-67`, `89991234567` и аналогичных, а хранится как `+79991234567`. ФИО очищается от лишних пробелов. Совпадение нормализованного телефона и ФИО без учёта регистра считается очевидным дубликатом и возвращает `409`; SHA-256 `duplicate_key` дополнительно защищён UNIQUE-ограничением PostgreSQL и не попадает в API. Невалидные данные возвращают `422`, отсутствующая карточка — `404`.

## Планирование процедур ухода

Список и отдельные страницы формы доступны по маршрутам `/procedures`, `/procedures/new` и `/procedures/{id}/edit`. Процедура связывает животное, тип процедуры и ответственного волонтёра, а также содержит плановую дату/время, целую положительную продолжительность, статус и комментарий до 255 символов. Статусы: `assigned` («Назначена»), `completed` («Выполнена»), `cancelled` («Отменена») и `overdue` («Просрочена»). При создании статус не принимается от клиента и всегда устанавливается сервером в `assigned`; PATCH не позволяет установить `completed`. Форма отображает статус без возможности редактирования. Переходы статусов появятся вместе с отдельным учётом фактического выполнения.

Новые назначения запрещены для архивных животных и неактивных волонтёров; эти же правила повторно проверяются при `PATCH` ссылочных полей. Форма предлагает только доступные карточки. Seed создаёт четыре типа: «Кормление», «Выгул», «Уборка» и «Обработка». Главная панель получает реальные количества и расписание на текущую дату.

## Учёт выполнения процедур

Для процедур в статусе `assigned` или `overdue` в списке доступно действие «Выполнить» и страница `/procedures/{id}/execute`. Сохранение создаёт фактический результат и в той же транзакции переводит процедуру в `completed`. Выполненные и отменённые процедуры выполнить нельзя. Одна процедура имеет не более одного выполнения — это защищено проверкой сервиса и UNIQUE-ограничением PostgreSQL.

Запись выполнения содержит фактические дату и время, обязательный результат, необязательный комментарий до 255 символов и серверное время создания. Результат отображается в карточке процедуры и может быть уточнён через PATCH. Удаления выполнения нет. Показатель «Выполнено сегодня» считается по `procedure_executions.execution_date`, а не по текущему статусу плана.

## Схема и API

```text
animal_types (1) ─── (N) breeds
animal_types (1) ─── (N) animals
breeds       (1) ─── (N) animals

volunteers — самостоятельный реестр команды
animals              (1) ─── (N) care_procedures
volunteers           (1) ─── (N) care_procedures
care_procedure_types (1) ─── (N) care_procedures
care_procedures      (1) ─── (0..1) procedure_executions
```

- `animal_types`: уникальное название типа.
- `breeds`: тип, название, необязательные границы веса. Название уникально внутри типа; границы пока не задаются seed и не используются как медицинские ограничения.
- `animals`: карточка с весом, годом рождения, контактами, примечанием, enum-статусом и внутренним ключом дубликата. Составной FK `(breed_id, animal_type_id)` гарантирует принадлежность породы выбранному типу даже при прямой записи в БД. CHECK-ограничения защищают вес, год и статус.
- `volunteers`: ФИО, нормализованный телефон, примечание и enum-статус `active`/`inactive`. CHECK-ограничения защищают непустое ФИО, формат телефона и статус; по статусу создан индекс.
- `care_procedure_types`: уникальные названия типов процедур.
- `care_procedures`: плановое назначение с FK на три реестра, enum-статусом и CHECK `duration_minutes > 0`; индексы созданы по дате, статусу, животному и волонтёру.
- `procedure_executions`: единственный фактический результат процедуры с датой, временем и `created_at`; UNIQUE по `care_procedure_id` исключает повторное выполнение.

## Проверки

Backend, из `backend` при запущенном PostgreSQL:

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m alembic check
```

Тесты используют реальные миграции и PostgreSQL из настроенного `.env`. Каждый тест создаёт отдельную случайно названную схему `lapka_test_*` в транзакции; после теста транзакция откатывается вместе со схемой. Рабочие таблицы не очищаются. Пользователю БД нужно право CREATE SCHEMA (у локального пользователя Docker оно есть). Тестируются API, валидация, FK/UNIQUE/CHECK, архивирование, фильтры, идемпотентность seed, upgrade/downgrade. При недоступной БД тесты завершаются ошибкой, а не пропускаются.

Frontend, из `frontend`:

```powershell
npm.cmd run lint
npm.cmd run build
npx.cmd playwright install chromium
npm.cmd run test:e2e
```

Браузерные тесты сами запускают Vite на `127.0.0.1:5174`. Используют тестовые ответы API и не создают записей в рабочей базе; проверяют основные модули, формы, фильтры, выполнение процедур, ошибки сервера и мобильную ширину. Реальную серверную логику и БД проверяет pytest. Скриншоты/трассы сохраняются в игнорируемом `frontend/test-results/`.
